# الدفع في المشروع خطوة بخطوة

ده دليل للنسخة المعدلة على branch المراجعة، مش تصريح بتشغيل دفع حقيقي. فيه بوابات لسه مفتوحة في PHASE0-REMEDIATION.md، أهمها التزامن في SQL والتسوية مع Stripe. مفيش migration اتعملت أو اتطبقت، ومفيش بيانات development أو production اتغيرت.

## الفكرة بمثال

منتج سعره 12.34 دولار. العميل بيضيفه للسلة. السيرفر يعيد حساب السعر من الكتالوج عند إنشاء الأوردر، ويسجل 12.34 USD، يعني 1234 سنت.

1. الزائر يقدر يتسوق من غير حساب. الواجهة تنشئ سلة من `POST /api/v1/cart/session` وتحفظ `cartId` والتوكن اللي بيرجع مرة واحدة.
2. أي تعامل مع سلة الزائر يحتاج `X-Cart-Token`. رقم السلة لوحده مش صلاحية. التوكن زي مفتاح للسلة، مايتحطش في URL أو logs.
3. لما يضغط checkout وهو مش مسجل، `POST /api/v1/orders` يرجع 401. الواجهة هي اللي توديه لصفحة التسجيل/الدخول. الـAPI مش بيفتح الصفحة بنفسه.
4. بعد الدخول، الواجهة تبعت access token مع توكن السلة إلى `POST /api/v1/cart/{cartId}/claim`. المحتويات بتفضل موجودة، والسلة بتبقى ملك الحساب، والتوكن القديم بيتلغي. أي سلة قديمة للحساب بتفضل منفصلة، مش بنمسحها أو ندمجها تلقائيًا.
5. الواجهة تنشئ أوردر من السلة المملوكة للحساب. العملة ثابتة USD، والأسعار من السيرفر، وأي عنوان لازم يكون ملك نفس المستخدم.
6. تطلب صفحة الدفع من `POST /api/v1/payments/checkout-session` بجسم `{"orderId":"the-created-order-id"}` ومع access token.
7. السيرفر يرجع `checkoutSessionUrl`. الواجهة تفتح الرابط. بيانات الكارت بتتكتب في صفحة Stripe، مش في مشروعك.
8. Stripe يبعت رسالة موقعة إلى `POST /api/v1/payments/webhook`. ده webhook.
9. السيرفر يفحص التوقيع، والسلة المالية: paymentId وorderId وsession والـpayment intent لو معروف، والمبلغ والعملة. لو الدفع paid فعلًا، يسجل Paid ويأكد الأوردر لو كان Pending.
10. صفحة النجاح تعرض نتيجة من API القراءة، مش تغيّر حالة الدفع. رجوع العميل لصفحة النجاح أو status=complete لوحده مش دليل إن الفلوس وصلت.

## إيه اللي يتجهز عندك

- قاعدة اختبار منفصلة تجهزيها إنتي بعد مراجعة الـschema. مفيش أوامر migration في الدليل ده، وممنوع استخدام إنشاء تلقائي بدلها.
- frontend فيه صفحة تسجيل/دخول وصفحة نجاح وصفحة إلغاء. المشروع ده backend، الصفحات والتنقل وتخزين access token/guest token مش منفذين هنا.
- حساب Stripe مناسب للاختبار. إنشاء حساب تجاري حي وتوفر الخدمة للكيان والدولة ليهم شروط منفصلة، الدليل مش تأكيد إن مشروعك مؤهل للتحصيل الحي. ماتستخدميش عنوان أو كيان غير صحيح للتحايل على الشروط.
- test secret key وwebhook signing secret مختلفين. الأول يسمح للسيرفر يطلب session، والتاني يتحقق من رسائل webhook. مفاتيح test وlive مش بدائل لبعض.

## إعدادات الاختبار الخاصة

حطي القيم الحقيقية عندك في ملف الإعدادات الخاص غير المرفوع أو environment variables. ماتبعتليش المفاتيح هنا، وماترفعيش الملف على GitHub.

| الإعداد | وظيفته |
|---|---|
| `Stripe__SecretKey` | مفتاح اختبار السيرفر، بيبدأ عادة بـsk_test |
| `Stripe__WebhookSecret` | سر توقيع الـwebhook من مستمع CLI للاختبار المحلي، أو من endpoint الاختبار نفسه |
| `Stripe__ClientUrl` | أصل عنوان frontend بتاعك |
| `Stripe__SuccessPath` | مسار صفحة النجاح، الافتراضي `/payment/success` |
| `Stripe__CancelPath` | مسار صفحة الإلغاء، الافتراضي `/payment/cancelled` |
| `DataInitialization__Enabled` | يفضل false، تشغيله يكتب seed data، مش خطوة مطلوبة للدفع |

العملة من تسعير السيرفر USD. تغيير Stripe__Currency مش بيحوّل أسعار المنتجات لعملة تانية.

## توصيل webhook محليًا، بعد تجهيز بيئة الاختبار

بعد مراجعة بوابات الإصدار وتجهيز قاعدة الاختبار الخاصة بيكي:

1. شغلي API وخدي عنوان الاستماع الفعلي من console. Swagger متاح في Development فقط، و`/api/v1/health` فحص حياة للتطبيق مش اختبار قاعدة البيانات.
2. ثبتي Stripe CLI من المصدر الرسمي وسجلي الدخول لحساب الاختبار عندك.
3. شغلي الأمر التالي بعد استبدال `YOUR_LOCAL_API_ORIGIN` بعنوان API الفعلي، مش frontend:

```bash
stripe listen --events checkout.session.completed,checkout.session.async_payment_succeeded,checkout.session.async_payment_failed,checkout.session.expired --forward-to YOUR_LOCAL_API_ORIGIN/api/v1/payments/webhook
```

4. خدي signing secret اللي CLI بيعرضه وحطيه في إعدادات webhook الخاصة، وأعيدي تشغيل API لو الإعدادات بتتقري عند البداية. سر endpoint الموجود في Dashboard مش بالضرورة نفس سر CLI.
5. اعملي session من أوردر حقيقي موجود في قاعدة الاختبار. افتحي الرابط الراجع، واستخدمي وسيلة اختبار من صفحة Stripe الرسمية، مش كارت حقيقي. نجاح synthetic trigger من غير payment مطابق في قاعدة الاختبار مش اختبار كامل للتدفق، وغالبًا هيرفضه فحص الهوية.
6. اتأكدي إن webhook استلم 2xx، وبعده استعلمي عن الدفع والأوردر من API. ماتكتفيش بصفحة النجاح.

## إزاي تعرفي النتيجة

| الحالة | معناها |
|---|---|
| Pending | محاولة اتسجلت أو صفحة لسه مفتوحة، مفيش تأكيد دفع |
| Processing | session اكتملت لكن النتيجة المالية لسه منتظرة |
| Paid | حدث موقّع مطابق أثبت paid |
| Failed / Expired | محاولة انتهت، إعادة المحاولة تعمل سجل جديد من غير مسح القديم |
| Refunded | سجل نهائي، مش معناه إن الكود هنا نفّذ رد فلوس عند Stripe |
| 409 | في عملية لسه محتاجة نتيجة أو تسوية، ماتعمليش loop يفتح sessions جديدة |

لو session اتعملت عند Stripe وحفظ الرابط فشل محليًا، نفس العملية بتتعاد بنفس identity ومفتاح idempotency. لو المحاولة غير المحسومة قديمة، الكود يوقفها للتسوية بدل المخاطرة بدفعة جديدة. لسه مطلوب إجراء تشغيلي للمحاولات العالقة والدفعات المتأخرة، واختبار تزامن SQL قبل التشغيل الحي.

إلغاء أوردر في قاعدة البيانات مش refund عند Stripe. وإغلاق صفحة الدفع مش إلغاء مؤكد عند المزود. لو حصل دفع متأخر لأوردر اتلغى، الكود يحفظ واقع الدفع لكنه مايرجعش الأوردر للحياة؛ دي السياسة اللي وافقتي عليها: الدفع يبقى Paid، والأوردر يفضل Cancelled، وحدث الدفع يتسجل عليه ManualReviewRequired للمراجعة اليدوية. مفيش شحن تلقائي أو رد فلوس تلقائي. حتى لو المحاولة اتسجلت Failed أو Expired قبل كده، إثبات دفع صحيح ومتطابق لأوردر ملغي بيتسجل Paid. سجل Refunded ما بيتغيرش.

المراجعة مش شاشة جديدة في البرنامج: مسؤول تقني بصلاحية قراءة قاعدة البيانات يراجع سجلات StripeWebhookEvents اللي ProcessingResult فيها ManualReviewRequired، ويربطها بالدفع والأوردر عن طريق PaymentId. يقارنها بحساب Stripe، وبعدها أي قرار رد فلوس يكون منفصل. مفيش إجراء آلي لمسح علامة المراجعة أو إصدار refund. إلغاء أوردر مدفوع أصلًا، ومدة حجز المخزون، وقواعد الكوبون عند الإلغاء لسه قرارات منفصلة.
