## Stop before deployment: SQL concurrency and schema

P05/E03 remain open. Do not treat an application-process lock, a single SaveChanges call or EF InMemory as proof of database serialization. Recommended next design for owner review:

1. Add SQL-backed transaction/locking or concurrency-token abstractions at the infrastructure boundary. Use short critical sections for checkout reservation, claim, payment creation and webhook state/event recording. Do not hold a SQL transaction over a Stripe network call.
2. Enforce a durable one-active-attempt-per-order rule and an exactly-once cart-to-order conversion invariant, with a documented retry/reload policy for conflicts. Existing schema has no Order.CartId link, so durable conversion uniqueness requires an owner-reviewed schema design, not an invented migration.
3. Protect variant stock conditional decrement/restock, order transition and coupon global/per-user usage atomically across requests and processes. Include inventory admin writes and returns in the analysis, not checkout alone.
4. Parallel isolated SQL tests must prove: same cart two checkouts produce one order; two orders competing for final unit do not oversell; duplicate/different out-of-order Stripe events cannot regress/duplicate payment or confirm twice; concurrent claim has one owner; coupon global/per-user cap holds; cancel retries restock once; two checkout requests use one active operation.
5. Handle DbUpdateConcurrencyException and verified provider-specific unique violations with rollback/reload, never broad swallow. The current webhook duplicate catch names only the event-id constraint, but provider-specific error-code discrimination still needs SQL testing.

No concurrency entity/config schema patch was added by guessing. This section is a design proposal, not implemented protection.

## Operational payment gates

Reconcile old pending attempts with no session before Stripe idempotency retention can lapse. Current code conservatively stops automatic recovery after 23h; changing client URLs/session parameters during same-operation recovery can also create provider parameter conflicts. Reconcile in provider dashboard/support workflow, do not mint a new charge blindly. A signed event arriving before local session-id save is rejected for retry rather than trusted on metadata alone. Alerts, dead-letter processing, reconciliation job and automatic expiry recovery are not implemented.

Owner approved on 24 November: if cancellation precedes a verified successful payment notification, keep OrderStatus.Cancelled, record PaymentStatus.Paid/PaidAt and flag the existing StripeWebhookEvent.ProcessingResult as ManualReviewRequired. This also accepts valid matching success over a local Failed/Expired attempt for cancelled orders only; it does not reverse Refunded. The original durable review record remains; a distinct repeat-success event is ignored once Paid and same event-id retry is deduplicated. Payments already Paid before this handler sees a cancelled order are not newly classified, keeping paid-then-cancel policy separate. Later failure/expiry cannot downgrade Paid. No confirmation history, stock/coupon change, provider call, automatic fulfillment or refund is triggered. All financial identity/amount/currency/signature checks still apply before mutation.

Manual operations: an authorized database reviewer should inspect existing StripeWebhookEvents records with ProcessingResult equal to ManualReviewRequired, follow PaymentId to the Paid payment and cancelled order, and verify provider evidence before deciding separately on a refund. This is a durable classification in an existing column, not an admin queue, notification, scheduler or review-resolution workflow. Do not relabel money Failed to clear it. No review-resolution mutation or automatic refund is provided. Existing schema already contains this column; no entity/config/migration/snapshot change is needed for this policy. InMemory reload and signed-payload tests prove sequential persistence, not SQL concurrency.

A late successful payment for another order no longer Pending records the financial fact without resurrecting fulfillment. Owner additionally approved on 24 November: ordinary admin cancellation of an already-paid order requires manual review first. The status-update path returns HTTP 409 with a review-required message when any included payment attempt is Paid, before restock, history, order/payment mutation or save. It checks every attempt, not just the newest one. Existing allowed non-cancellation transitions and unpaid cancellation remain unchanged. Repeating Cancelled for an already-cancelled order stays a no-op. This guard adds no review record, queue, notification, review approval endpoint or refund operation; it does not grant a later override. No existing column can safely represent a separate approved-review lifecycle without a design decision, and no schema is changed. Admin must stop and get an authorized review outside this ordinary status endpoint. Four HTTP/InMemory cases and five unit cases cover the guard and retries. Customer cancellation behavior is not changed by this admin-only approval. SQL serialization against concurrent payment/cancellation still requires P05/E03.

Expired/unpaid stock reservations, refunds, chargebacks and zero-total fulfillment still need an approved policy and operational path. Changing database PaymentStatus to Refunded is not a Stripe refund. No live refund is implemented or issued.
